# 15_架构方案评审意见

> 文档状态：历史评审记录。本文保留当时问题和决策过程，不作为当前对象模型事实源。
> 当前有效口径以 `01`、`03`、`09`、`10`、`14` 及最新已采纳评审决策为准。

## 1. 评审目标

本文用于承接对 `14_技术架构选型与系统架构图.md` 的架构评审讨论，回答一个关键推进问题：

```text
当前发现的架构问题，是先按建议优化设计后再继续后续任务，
还是先继续跑通流程，之后再统一优化？
```

评审结论不是要求立刻进入完整技术详细设计，而是先识别“现在不修、后续返工成本会明显升高”的架构边界，并给出最小修订策略。

## 2. 总体判断

`14` 的主方向成立：

- MVP 采用 `本地 Web + 本地服务` 是合理选择。
- `WorkflowSpec` 文件化、可 diff、可 Git 管理的方向正确。
- Mermaid 作为架构源、PNG 作为展示资产的分工合理。
- Run/Event 以 JSONL 起步、后续再用 SQLite 做索引层，适合作为 MVP 的渐进路线。
- Node DAG 优先、Infinite Canvas 后置增强，符合当前 MVP 验证顺序。

但 `14` 中也存在几类会影响后续实现成本的架构问题：

- 本地服务安全边界不足。
- 状态模型容易混写。
- `WorkflowSpec` 的“唯一真相”表述过大。
- JSONL 运行日志缺少恢复和幂等语义。
- ProviderRouter、Adapter、NodeSpec 的职责边界还需收口。
- React Flow 与 tldraw 同时作为一等编辑器会提前放大同步成本。

因此不建议完全跳过优化直接继续后续任务，也不建议现在停下来做大规模重构。

## 3. 决策结论

推荐采用：

```text
先做一次轻量架构修正关口，再继续后续任务。
```

也就是先优化 20%-30% 的关键设计，修掉后续返工最贵的边界问题，再继续进入产品信息架构、页面地图和原型规划。

这次修正的目标不是追求架构完美，而是保证后续 `15/P2/P3/P4` 不建立在错误或含混的状态、数据和安全边界之上。

## 4. 两种推进方式对比

| 方案 | 做法 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| 先继续跑通流程，之后再优化 | 暂不修订 `14`，直接进入产品 IA、原型或 MVP 流程验证 | 推进速度快，能尽早看到端到端体验 | 状态、Trace、Gate、Artifact、安全边界后续可能全线返工 | 不推荐作为主路线 |
| 先完整优化架构，再继续任务 | 把所有技术细节、状态机、安全、存储、Adapter 都展开到详细设计 | 架构最稳，后续实现风险低 | 容易把 P1.5 拖成 P3，节奏变慢，过早设计未验证细节 | 不推荐现在做 |
| 轻量修正关键边界，再继续任务 | 只修正高返工成本问题，保留未验证细节到 P3 | 兼顾推进速度和架构稳定性 | 需要控制修订范围，避免扩张 | 推荐 |

## 5. 为什么不能完全先跑通流程

### 5.1 状态模型会污染多个核心模块

当前文档体系中已经明确：

- `reviewing` 是 Agent 状态。
- `pending_review` 是 Gate / Artifact / NodeRun 状态。
- `approved / rejected / blocked / skipped` 应落在 GateDecision、Artifact 或 NodeRun 层，而不是混入 AgentHealth。

如果不先收口状态分层，后续会同时影响：

- Node DAG 的节点状态展示。
- AgentHealth Dashboard 的健康卡。
- Artifact Board 的产物状态。
- Gate Review 的下游放行判断。
- TraceEvent 和 Evolution 的事件归因。

这类问题一旦进入 UI 和日志结构，后续改动成本会很高。

### 5.2 “唯一真相”边界不清会影响数据模型

当前 `WorkflowSpec 是唯一真相` 的方向需要修正为：

```text
WorkflowSpec 是模板与编排真相。
RunSpec / NodeRun / TraceEvent / ArtifactManifest / GateDecision 是运行事实真相。
```

如果不提前澄清，后续可能出现两类问题：

- 把真实 run 的状态、产物路径、审核结果误写回 workflow 模板。
- Evolution 更新模板和运行复盘之间的边界不清，导致 stable workflow 被间接污染。

### 5.3 本地服务安全边界必须前置成架构规则

`本地 Web + 本地服务` 一旦具备文件读写、CLI 调用、MCP 调用和外部 API 调用能力，就必须先规定安全边界。

MVP 不一定要实现复杂权限系统，但架构文档至少需要明确：

- Local Service 只监听本机地址。
- UI 请求需要 origin / token / session 校验。
- 读写路径必须限制在 workspace allowlist。
- CLI、MCP、外部 API 必须走 tool allowlist。
- 危险操作需要显式确认和审计事件。
- 凭证只允许引用，不允许写入 spec、trace 或 Git。

否则后续即使流程跑通，也会留下不适合产品化的本地执行风险。

### 5.4 JSONL 运行日志需要最小恢复语义

JSONL 作为 MVP 起点是合理的，但如果要支持 Run Queue、Recovery、Resume 和 Gate Review，至少需要定义：

- 每条事件有稳定 `event_id`。
- 同一 run 内有递增序号或可排序时间戳。
- 节点执行有幂等键，避免重复 side effect。
- crash 后可以从 JSONL + manifest 重建 run 状态。
- retry / fallback / resume 必须写入审计事件。
- 外部副作用节点必须区分 dry-run、preview、real-run。

这些规则不先定，后面真实运行一旦中断，系统很难判断“该继续、该重试，还是已经完成”。

## 6. 为什么也不应该现在全面大改

`14` 还处在 P1.5 技术架构选型阶段，不应该提前承担 P3 技术详细设计的全部职责。

现在不宜展开到以下程度：

- 完整数据库 schema。
- 完整 CLI runner 实现。
- 完整权限系统。
- 完整状态机代码。
- 完整 adapter SDK。
- React Flow 与 tldraw 的完整双向同步实现。
- SQLite 索引层的详细查询模型。

这些内容应该在后续技术详细设计或 MVP 实现中基于原型验证逐步展开。

## 7. 本轮必须先修的架构决策

建议在继续后续任务前，先对 `14` 或后续修订文档固化以下决策。

### 7.1 Spec 与 Run 的真相边界

推荐表述：

```text
WorkflowSpec / ComponentSpec / AgentSpec / ProviderPolicy 是可版本化配置真相。
RunSpec / NodeRun / TraceEvent / ArtifactManifest / GateDecision 是运行事实真相。
Visual Builder、YAML/JSON、CLI/SDK 都只是编辑器或视图。
```

关键规则：

- UI 编辑 workflow 时生成 spec diff。
- 运行态事件不直接改写 stable WorkflowSpec。
- Evolution 只能生成建议、draft 或 experimental override。
- stable workflow 变更必须经过人工确认。

### 7.2 状态分层

建议明确四类状态：

| 对象 | 状态范围 | 说明 |
|---|---|---|
| AgentHealth | `idle / queued / running / waiting / blocked / reviewing / done / failed` | 描述 Agent 当前行为与健康 |
| NodeRun | `not_started / queued / running / pending_review / blocked / failed / rejected / skipped / done` | 描述节点实例执行状态 |
| GateDecision | `pending_review / approved / auto-approved / rejected / commented / blocked / skipped` | 描述审核门决策 |
| Artifact | `draft / pending_review / approved / rejected / archived / external_only` | 描述产物可用性 |

关键规则：

- `pending_review` 不写入 AgentHealth。
- `reviewing` 不作为 GateDecision 的持久状态。
- 下游放行只看 GateDecision 和 Artifact 状态，不只看 Agent 状态。
- 非法状态跳转必须拒绝并记录审计事件。

### 7.3 Local Service 安全边界

建议补充为架构硬规则：

- Browser UI 不直接访问文件系统、CLI、MCP 或外部 provider。
- Local Service 默认只绑定 `127.0.0.1`。
- 所有写操作必须经过 workspace allowlist。
- 所有 adapter 调用必须经过 provider policy 和 tool allowlist。
- 所有凭证只使用 env/keychain/local private config 引用。
- 所有危险操作记录 AuditEvent。

### 7.4 JSONL 恢复与幂等规则

建议 MVP 最小规则：

- `TraceEvent` 必须包含 `event_id`、`run_id`、`node_id`、`ts`、`event_type`。
- 节点执行请求必须包含 `run_id + node_id + attempt` 组成的幂等键。
- `ArtifactManifest` 必须记录 `produced_by`、`source_event_id`、`hash/path/status`。
- Run 状态由 `RunSpec snapshot + TraceEvent JSONL + ArtifactManifest + GateDecision` 重建。
- SQLite 后续只做索引层，不替代源事件和 manifest。

### 7.5 ProviderRouter 与 Adapter 边界

推荐调整为：

```text
ProviderRouter 负责选择 runtime adapter、provider、fallback 和执行策略。
Runtime Adapter 负责把 NodeRun 请求翻译成平台调用。
Adapter 返回 result、events、artifacts 和 failure metadata。
Adapter 不直接修改 WorkflowSpec / NodeSpec。
```

### 7.6 Infinite Canvas 的 MVP 降级策略

建议把 Infinite Canvas 在 MVP 中定位为：

```text
轻量原型与空间组织视图，暂不作为与 Node DAG 同等级的一等执行编辑器。
```

落地策略：

- 第一优先级是 Node DAG + Spec diff + RunTrace。
- Canvas 可以展示任务卡、素材卡、产物卡和节点卡。
- Canvas 中“任务卡转节点”必须进入 dry-run。
- Canvas layout 不参与执行顺序。
- React Flow / XYFlow 先承载严肃 DAG 编辑。
- tldraw 先验证空间体验，复杂同步后置。

## 8. 本轮可以暂缓的事项

以下内容不必在当前评审修订中完整解决：

- SQLite 具体表结构。
- 完整本地账号或多用户权限。
- 真实后台调度平台。
- 完整 adapter SDK。
- 完整图形化 diff。
- 多人协同冲突解决。
- 云同步、云端模板市场、多租户。
- tldraw 与 React Flow 的完整双向实时编辑同步。

这些内容只需在 `14` 中保留方向和引入时机，后续进入 P3/P4 再细化。

## 9. 建议执行顺序

推荐下一步按以下顺序推进：

1. 更新 `14_技术架构选型与系统架构图.md`，加入“架构修订决策”小节。
2. 把 Spec/Run 真相边界、状态分层、本地服务安全、JSONL 恢复语义写入 `14`。
3. 将 Infinite Canvas 的 MVP 定位改为轻量原型，不抢 Node DAG 的主线优先级。
4. 再进入产品侧信息架构和原型设计规划。
5. 在产品 IA 中所有页面状态、审核动作、产物状态都引用修订后的状态分层。
6. P3 技术详细设计时，再把 JSONL、SQLite、Adapter、权限和同步机制展开成实现任务。

## 10. 修订验收标准

完成本轮轻量架构修订后，应满足：

- 能清楚回答 `WorkflowSpec` 和真实运行数据分别保存什么。
- 能清楚回答每个状态属于 Agent、NodeRun、Gate 还是 Artifact。
- 能清楚回答本地服务能访问哪些路径、能调用哪些工具、如何记录危险动作。
- 能清楚回答 run 中断后如何从 JSONL 和 manifest 恢复。
- 能清楚回答 ProviderRouter 和 Runtime Adapter 谁负责选择、谁负责执行、谁负责记录。
- 能清楚回答 MVP 为什么先做 Node DAG，再做轻量 Infinite Canvas。

## 11. 最终建议

本次评审建议：

```text
先进行关键架构优化，再继续后续任务。
```

但优化范围必须严格控制在“高返工成本边界”上，不进入完整工程实现设计。

这条路线可以避免后续产品原型、运行态日志、审核门和多 Agent 看板建立在含混模型上，同时不会因为过度设计拖慢 Miracle 从方案文档进入原型验证的节奏。
